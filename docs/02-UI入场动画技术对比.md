# Web 前端 UI 元素交错入场动画 · 技术对比与实现方案

> 目标宿主：DeepSeek Harness 桌面版 Web 前端（React SPA，CSS Modules hash 类名，构建产物已打包压缩，不可改源码、不可重建 bundle）。
> 施加方式：页面文档加载后注入「一段样式 + 一段脚本」。
> 本文所有「实测」结论均来自本机无头 Chrome 154 的 CDP 逐帧采样与截图，方法与原始数据见文末附录 A / B。

---

## 0. 结论先行

**最终推荐：`@starting-style` + CSS 自定义属性负责「首帧无闪烁」，Web Animations API（`element.animate()`）负责「交错编排与执行」。** 不使用 View Transitions，不用 MutationObserver 加类名的快照法，不依赖任何 hash 类名。

理由一句话：本场景唯一真正稀缺的资源是「元素首次渲染前的那一帧」——只有 `@starting-style` 能在它之前生效；而动画的执行与编排交给 WAAPI，才能绕开「CSS 过渡需要变量跨帧变更」的时序陷阱，并获得可靠的 `finished` 回调与随时中断能力。

## 1. 挂钩方式对比

### 1.0 先厘清一件事：这个前端的 DOM 里到底有什么可挂的

从前端 bundle 解包后的真实代码（`@deepseek-ai/dsh-client-ui-*`）确认：

| 钩子 | 位置 | 稳定性 | 来源 |
| --- | --- | --- | --- |
| `#root` | 应用挂载点，`index.html` 里写死 | 极高 | 解包 `dist/index.html` |
| `#root > div`（AppFrame） | 布局根，CSS grid 容器 | 高（结构位置固定） | `client-ui-layout` 的 `AppFrame` 组件 |
| `[data-sidebar-collapsed]` `[data-rightbar-collapsed]` `[data-rightbar-fullscreen]` `[data-dragging]` `[data-animating]` | 挂在 AppFrame 上 | 高（语义属性） | 同上，JSX 属性列表 |
| `[data-shell-overlay]` `[data-shell-leading]` | AppFrame 的两个直接子元素 | 高 | 同上 |
| `[data-slot="root"]` `[data-slot="main"]` `[data-slot="sidebar"]` `[data-slot="rightbar"]` `[data-slot="sidebar.right.*"]` `[data-slot="conversation.session"]` | slot 锚点 | 高 | `renderSlot(key)` 渲染为 `<div data-slot=key style="display:contents">` |
| `[data-phase]`（`hero` / `active`）、`[data-content-phase]` | 对话区根元素 | 中（取值随版本变化） | `client-ui-conversation` 的 CSS Modules 选择器 |
| `[data-window-drag]` `[data-window-drag-recall]` | 标题栏拖拽区 | 中 | `web-frontend` bundle |
| `class="BynINW_frame"` 之类 | 全部布局类名 | **不可用** | CSS Modules 运行时 hash，形如 `Dc7zOa_root` / `Hqq-bq_fish` / `BynINW_frame` |

**关键坑（决定了一切方案的设计）：`[data-slot]` 锚点是 `display: contents` 的。**

```js
// client-ui-renderer/lib/client.js
const ANCHOR_STYLE = { display: "contents" };
// <div data-slot={slotKey} style={ANCHOR_STYLE}>…</div>
```

`display: contents` 的元素**不生成盒子**：`getBoundingClientRect()` 全 0，`transform`/`opacity` 对它无效。所以：

- 不能把 `[data-slot="main"]`、`[data-slot="root"]` 这类锚点当动画目标；
- 真正可以动画的盒子是 **AppFrame 的 grid 子元素**（`sidebarCol` / `centerCol` / `rightbarCol` / `overlayLayer`），而这些恰好**没有语义属性**；
- 结论：动画目标必须**运行时用几何计算挑出来**（见第 3 节），这也是本方案里唯一需要动脑的地方。

### 1.1 纯 CSS 属性 / 结构选择器

| 手段 | 可用性 | 说明 |
| --- | --- | --- |
| `[data-*]` 属性选择器 | **可用（主力）** | 语义属性是唯一稳定的钩子。AppFrame 上的 `data-*-collapsed` 可直接用于「侧栏是否参与入场」的判定。 |
| `:has()` | 可用但**本场景用不上** | 实测 `CSS.supports('selector(:has(*))') === true`（Chrome 154）。但布局列本身没有可辨识的后代特征，`:has()` 无法把「左栏/右栏」与「中栏」区分开——它只能解决「某元素内部有没有 X」，解决不了「某元素是第几列」。 |
| `:nth-child` / `:first-child` | **不可用** | AppFrame 的子元素数量与顺序随运行时状态变化：`leadingMounted = darwin && sidebarCollapsed` 会插入 `data-shell-leading`；`!sidebarCollapsed` 才渲染 `DragHandle`；右栏按 `layoutInfo.rightbarShown` 条件渲染。索引不稳定，一改就错位。 |
| 类名选择器 | **禁用** | CSS Modules hash，形如 `Dc7zOa_root`。版本一变全废。 |

**结论：`[data-*]` 作辅助判定可用；纯结构选择器（`:nth-child` 系）在本场景不可用。**

### 1.2 注入 `<style>` + CSS 自定义属性驱动

思路：注入样式表，用 `--enter-x` / `--enter-o` 之类变量描述起点与终点，再由脚本改变量触发过渡。

**实测结论：作为「首帧」手段完全可用，作为「动画驱动」手段有硬时序陷阱。**

实测（Chrome 154，探针 A / C，逐帧 `getComputedStyle` 采样）：

| 场景 | 结果 |
| --- | --- |
| 变量在**元素首次样式解析之前**就有值，配合 `@starting-style` | 首帧即起点，过渡正常播放，`transitionend` 在 490ms 触发（duration 400ms + 页面启动 ~70ms） |
| 变量在**同一个 rAF 回调内**先设起点再设回终点 | `transitionrun` 与 `transitioncancel` **同一毫秒**触发，元素**完全不动**（opacity 恒为 1，transform 恒为 0） |
| 变量在 `rAF` 内设起点、`setTimeout 0` 后设回终点 | 同样被取消，元素不动 |

**为什么**：CSS 过渡比较的是「相邻两次样式重算」的值。若两次变更落在同一帧的样式重算里，浏览器只看到「起点→终点」的净变化被中间态覆盖，或直接判定为取消。变量驱动要求**起点必须真实地存在过一帧**。

**适用性结论：可以用它定义首帧起点（配合 `@starting-style`），但不要把动画驱动权交给它**——时序太脆，且一旦被取消没有任何回调可感知。

### 1.3 Web Animations API（`element.animate()`）vs CSS transition

| 维度 | WAAPI | CSS transition |
| --- | --- | --- |
| 运行线程 | 对 `transform` / `opacity` 可跑在合成线程 | 同样可合成，但触发依赖样式重算 |
| 与 CSS 的优先级 | **覆盖 CSS 过渡**（实测见下） | 被 WAAPI 覆盖 |
| 中断能力 | `pause()` / `cancel()` / `finish()` + `finished` Promise | 只能靠改变目标值「打断」，无回调保证 |
| 首帧控制 | `fill: 'backwards'` 可在 delay 期间保持起点值 | 依赖 `@starting-style` 或先写起点 |
| 内联样式污染 | **无**（动画走独立时间线，实测 `element.style.cssText` 保持为空） | 需要写内联变量 |
| 清理 | `cancel()` 后样式完全回退到 CSS 计算值 | 需手动清变量 |

**实测 A：WAAPI 覆盖 CSS 过渡。** 元素正在跑 `transition: opacity 400ms`（CSS 类驱动），中途启动一个 `animate([{opacity:1},{opacity:1}], {duration:300, fill:'both'})`，随后 100ms 采样 `getComputedStyle().opacity === "1"`，而 `element.style.cssText === ""`（空）。说明 WAAPI 通过动画时间线压制了 CSS 过渡，且没有写内联样式。

**实测 B（重要坑）：`cancel()` 会跳回 CSS 过渡的当前值。** 同一场景下 200ms 后调用 `a.cancel()`，`opacity` 立刻变成 `0.291615`——那是 CSS 过渡此刻推进到的值。**视觉上是一次突跳。**

> **中断规范做法**：先 `animation.commitStyles()` 把当前值固化到内联样式，再 `cancel()`；或干脆用 `animation.pause()` 冻结，不做 cancel。

**实测 C：`fill: 'backwards'` 与 delay 配合。** 交错编排需要给每个元素不同 delay，`fill:'backwards'` 保证 delay 期间元素停在起点而不是终点的「跳变态」——这是 WAAPI 相对 CSS 过渡在编排上的决定性优势。

**适用性结论：本场景首选。**

### 1.4 `@starting-style` + `transition-behavior: allow-discrete`

**实测（Chrome 154.0.8037.95，探针 A）：**

| 检测项 | 结果 |
| --- | --- |
| 解析 `@starting-style` 规则 | 支持（样式生效） |
| `CSS.supports('transition-behavior','allow-discrete')` | `true` |
| 页面脚本第一行读 `getComputedStyle(#box).opacity` | `"0"`（即起始值） |
| 页面脚本第一行读 `getComputedStyle(#box).transform` | `matrix(1, 0, 0, 1, -80, 0)`（即起点位移） |
| 同一帧的对照组（无 `@starting-style`） | `opacity: "1"` |
| 首个 rAF（t=8.5ms） | 仍是起点值，**没有任何中间帧的「终值态」** |
| 过渡结束 | `transitionend` at t=415.5ms（duration 400ms） |

**这一条是整个方案的地基**：`@starting-style` 让元素在**第一次样式解析**时就被计算为起点值，因此浏览器从**首帧**就画的是「起点」，根本不存在「先画终值、再跳回起点」的中间态。

**关于 `transition-behavior: allow-discrete`：**

- 实测本机支持，但它解决的是**离散属性**（`display` / `content-visibility` / `overlay`）能否参与过渡的问题。
- **本场景用不到**：我们的入场只动 `opacity` 与 `transform`，二者都是连续可插值属性。
- 它真正有价值的场景是「元素从 `display:none` 变可见的同时做入场」——那需要 `@starting-style` + `transition-behavior: allow-discrete` 组合。DSH 的 AppFrame 是常驻节点（只是内容为空），不属于这种情况。
- 版本门槛：`@starting-style` 与 `transition-behavior` 在 MDN 上均标记为 **Baseline 2024 newly available**；具体首个支持版本号（Chrome 117 一档）**未在本机逐条核验**，本机 Chrome 154 实测支持（见附录 B）。

**适用性结论：首帧无闪烁的唯一原生 CSS 解。必用。**

### 1.5 View Transitions API

**实测（探针 D，headless Chrome 154）：**

| 检测项 | 结果 |
| --- | --- |
| `typeof document.startViewTransition` | `"function"` |
| `CSS.supports('view-transition-name','none')` | `true` |
| 返回值类型 | `[object ViewTransition]`，`ready` 是 thenable |
| 时序 | 调用 t=67.8ms → `ready` t=73.9ms → `finished` t=393.4ms |

**在 Electron / Chromium 里的限制（结合实测与框架特性）：**

1. **整页快照**：它把旧状态与新状态各截一张图做交叉淡入。对「逐元素 stagger 由外向内滑入」这种细粒度编排，表达能力不足——你能控制的只有 `::view-transition-*` 伪元素组，做不出每个元素独立 delay。
2. **一次只允许一个活跃过渡**：并发调用会抛错或被忽略。而 DSH 前端自身可能已在用（插件、路由切换）。
3. **会接管渲染树**：过渡期间页面被提升为独立合成层，滚动、输入、拖拽的响应会受影响；对桌面应用的常驻窗口不划算。
4. **`::view-transition` 伪元素命名与层级**需要全局管理，容易与现有 `z-index` 体系（如 `composerSeat` 的 `z-index:7`、菜单 `z-index:9`）冲突。
5. **headless / 非合成路径下**实测可用（上面数据），但这只证明 API 存在，不证明它在真实 DSH 窗口里的观感与性能。

**适用性结论：不推荐用于首次加载入场。它适合「路由/视图切换时的整页过渡」这一完全不同的问题。**

### 1.6 MutationObserver 侦测首次插入后加类名再触发

思路：`MutationObserver` 捕获元素插入 → 加 `enter` 类 → 下一帧再加 `enter--in` → 触发 CSS 过渡。

**实测（探针 B，Chrome 154）：**

| 观测点 | 结果 |
| --- | --- |
| 元素已在 DOM 中，JS 给它加 `.enter.init`（起点类）后立刻读 `getComputedStyle` | `opacity: "1"`，`transform: matrix(1,0,0,1,0,0)` —— **起点没生效** |
| 双 rAF 后移除 `.init` 放行 | `opacity: 0.958443` —— 过渡确实跑了，但**是从「已经画过终值」的 1 开始的** |
| 动态插入新元素后立刻加起点类 | 同样读到 `opacity: "1"` |

**这就是 FOUC / 闪烁的根因**：JS 能读到元素、能给元素加类，说明浏览器**至少已经为它算过一次样式、画过至少一帧**。那一帧画的是终值。于是顺序变成「终值 → 起点 → 终值」，中间那次跳变就是肉眼可见的闪。

**结论：**

- 若在样式表里**预先**给目标元素写死起点（`[data-x] { opacity: 0 }`），闪烁可避免——但那就等于「预先隐藏」，本质上是 `@starting-style` 的手工版本，还得自己管理「何时放行」，一旦脚本出错元素就永久不可见（**这是它的致命风险**）。
- 若依赖「插入后再加类」的快照法，**必然闪**，实测已证。
- 另有重复触发问题：React 重渲染会不断产生 `addedNodes`，需要额外的幂等标记。

**适用性结论：不推荐。它比 `@starting-style` 多做一步、慢一帧、且多一个「元素永久隐藏」的失败模式。**

---

### 1.7 推荐与依据

**推荐：`@starting-style` + CSS 自定义属性（首帧）＋ Web Animations API（编排与执行）。**

依据逐条对应上面的实测：

1. 首帧唯一性：只有 `@starting-style` 在「元素首次样式解析」阶段生效（1.4 实测，脚本第一行即读到起点值）。
2. 编排能力：`element.animate()` 原生支持每元素独立 `delay` + `fill:'backwards'`，无需 CSS 类状态机（1.3）。
3. 时序鲁棒性：绕开变量驱动的跨帧陷阱（1.2 实测：同帧改回必然取消）。
4. 可中断 / 可观测：`finished` Promise 让「播完即清理」有确定时机（1.3）。
5. 无类名依赖：动画目标由运行时几何判定选出，不碰任何 hash 类（见第 3 节）。
6. 零内联污染：实测 WAAPI 不写 `element.style`（1.3 实测 A），清理干净。

## 2. 不闪烁的硬约束

### 2.1 首帧到动画开始之间「闪一下」如何根除

**`@starting-style` 能做的：**

- 在元素**第一次**参与样式解析时，把指定属性计算为「起始值」。
- 保证浏览器**首帧**绘制的内容就是起点（`opacity: 0` + 偏移），而不是「先终值后跳回」。
- 实测证据：页面脚本执行的第一行（t=0.8ms）读 `getComputedStyle`，已是 `opacity: "0"` / `translateX(-80px)`；随后第一个 rAF（t=8.5ms）仍是起点，全程无中间态。

**`@starting-style` 做不到的：**

- **只在首次样式解析生效一次**。元素已经渲染过之后再改变量，它**不会再应用**。所以「元素已上屏后才注入脚本」这条路径，`@starting-style` 救不了（详见 2.2 的时序说明）。
- 它不负责动画本身，只负责「起点长什么样」。动画必须由 `transition` 或 WAAPI 承接。
- 它不能跨元素继承——每个元素的起始值要各自可解析（本方案用 CSS 变量 + 元素自身的 `@starting-style` 规则解决）。

**根除闪烁的三条硬规则：**

1. **注入脚本的第一件事**就是注入样式 + 在 `<html>` 上打「待入场」标记（`data-dsh-enter-pending`），不能等到「找到元素」再注入。
2. **起点值必须通过 CSS 变量在「元素首次样式解析之前」就已就位**——本方案在设置 `data-dsh-enter-ready` 标记的同一同步块里写入变量，标记与变量一起进入同一次样式重算。
3. **动画的启动要等两帧**（`rAF → rAF`）：第一帧让起点落定，第二帧再 `animate()`。实测最终版第 4 帧（t=22.2ms）三个元素同时处于起点，第 5 帧起才推进——没有中间态。

### 2.2 只在「应用首次加载」播放一次

**做法：`sessionStorage` 标记。**

```js
var KEY = 'dsh-enter-anim-played';
if (sessionStorage.getItem(KEY)) { /* 不播，直接清理标记 */ return; }
// … 播完（WAAPI finished 回调里）
sessionStorage.setItem(KEY, '1');
```

为什么是 `sessionStorage` 而不是内存变量：DOM 反复重建（React 重渲染、路由切换、面板开关）不会重置 `sessionStorage`；而刷新页面（F5）在同一标签会话里也**不会**重置它，所以刷新不会重播——这正是「只在应用首次加载」的语义。关掉窗口重开则是新会话，重新播一次。

**实测（探针 probe-lifecycle，150 帧逐帧采样）：**

| 场景 | `readyFrames` | `movedFrames` | `sessionStorage` |
| --- | --- | --- | --- |
| 首次加载 | 38 | 30 | 播完写 `"1"` |
| 后续 reload（同会话） | 0 | 0 | 保持 `"1"` |

即：首载时标记存在 38 帧、有 30 帧处于位移/半透明状态；reload 后**一帧都没有动过**。

**关于「DOM 反复重建」**：本方案不给元素挂任何类名、不装 MutationObserver，动画是 WAAPI 一次性对象，React 重渲染不会「重新触发」任何东西。唯一需要防的是「重复执行整个脚本」——`window.__DSH_ENTER_ANIM__` 幂等标记 + `sessionStorage` 双重拦截。

**一个边界（未实测，标注为未验证）**：如果注入脚本的时机**晚于** React 首次挂载（即 frame 已经上屏并画过一帧），那么这一帧画的是终值，随后动画会把元素拉回起点——**会看到一次闪**。本方案对此没有完全免疫。规避手段：尽量把注入放到 `document-start` 或 `DOMContentLoaded`，让脚本先于 React 挂载就位（本方案的 `requestAnimationFrame` 轮询等待就是为了适应「元素后到」的情形）。

### 2.3 「页面白屏 → 内容出现」而不是「白闪 → 内容跳入」

两者的差别在**首帧画什么**：

| | 白闪 → 内容跳入 | 白屏 → 内容淡入（目标） |
| --- | --- | --- |
| 首帧 | 内容以终值满不透明画出来 | 内容以 `opacity: 0` + 偏移画出来 |
| 第二帧 | JS 加类/改变量，内容跳回起点 | 保持起点 |
| 后续 | 从起点跑动画到终值 | 从起点跑动画到终值 |

差别只在前两帧，而这两帧决定观感。实现要点：

1. **`@starting-style` 把首帧定为起点**（这是唯一手段）。
2. **`<html>` 上的 `data-dsh-enter-pending` 标记**在整个「等待元素出现」阶段都保持——它同时承担两件事：给降级路径兜底（`opacity: 0`），以及抑制滚动条。
3. **背景不要留白**：DSH 的 `body`/`#root` 背景由主题变量决定（解包 CSS 里有 `--dsw-alias-bg-base`、`body[data-ds-dark-theme]` 等）。注入的样式只动 `opacity`/`transform`，**绝不改背景色**，这样首帧看到的是「深色底 + 几乎透明的内容」而不是「白底」。

**实测佐证**：截图 `shot-40ms.png`（t=112ms）里左、右两列几乎完全融入背景（`opacity: 0`，且已偏离 `±23.9px`），中间列半透明浮现；`shot-900ms.png`（t=972ms）三列完全到位。整个过程中**背景色始终是深色**，没有白闪。

### 2.4 `prefers-reduced-motion`

**做法：直接跳过动画，并一次性写入标记。**

```js
var reduce = window.matchMedia('(prefers-reduced-motion: reduce)');
if (reduce.matches) {
  sessionStorage.setItem(KEY, '1');   // 不再重播
  document.documentElement.removeAttribute('data-dsh-enter-pending');
  return;                              // 不创建任何 animation
}
```

**实测（`chrome --force-prefers-reduced-motion`）：**

| 检测项 | 结果 |
| --- | --- |
| `matchMedia('(prefers-reduced-motion: reduce)').matches` | `true` |
| 产生位移或半透明的帧数 | **0** |
| `data-dsh-enter-pending` / `data-dsh-enter-ready` | 均未残留 |
| 最终状态 | 三列全部 `opacity: 1`、位移 0 |

**设计取舍（需要明确记录）**：跳过动画时也写入 `sessionStorage` 标记，意味着「用户先开了减少动效、之后关掉」不会再补播。这是刻意的——减少动效是用户的持续性偏好，不该因为设置变化就补一次动画。如果希望「偏好关掉后下一次加载补播」，把那一行 `setItem` 去掉即可。

**建议同时保留 CSS 侧兜底**（脚本被拦截时的保险）：

```css
@media (prefers-reduced-motion: reduce) {
  #root > [data-dsh-enter-ready] > * { transition: none !important; animation: none !important; }
}
```

## 3. 元素分组与编排

### 3.1 无类名情况下如何结构性识别各区域

**判定顺序（从可靠到兜底）：**

**第一优先：语义属性直接命中。**

| 区域 | 判定 |
| --- | --- |
| 左侧边栏 | AppFrame 的 `[data-sidebar-collapsed]` 存在 ⇒ 侧栏折叠，不参与入场；否则它是 AppFrame 第 1 个 grid 子元素 |
| 右侧边栏 | `[data-rightbar-collapsed]` 存在 ⇒ 右栏宽度为 0，跳过；`[data-rightbar-fullscreen]` 存在 ⇒ 全屏态，按整列处理 |
| 底部输入框 | 对话区内部的 `[data-slot="conversation.session"]` 锚点下，`composerSeat` 是 `position: sticky; bottom: 0` 的座位（解包 CSS 可证） |
| 中间对话区 | 中心列 `centerCol` 是 grid 的 `minmax(400px, 1fr)` 列；其内部有 `[data-slot="main"]` 锚点 |

**第二优先（本方案采用）：几何判定。** 因为 grid 列本身没有语义属性，用运行时几何把 AppFrame 的直接子元素分类：

```js
var W = frameRect.width, H = frameRect.height;
for (var i = 0; i < frame.children.length; i++) {
  var k = box(frame.children[i]);              // 跳过 display:contents / 不可见 / 零尺寸
  if (!k) continue;
  var cx = k.r.left + k.r.width / 2;           // 元素水平中心
  var side  = cx < W * 0.45 ? -1 : (cx > W * 0.55 ? 1 : 0);   // 左列 / 右列 / 中间
  var depth = Math.min(1, Math.abs(cx / W - 0.5) * 2);        // 0=画面中心，1=最外缘
  var isBottom = k.r.bottom > frameRect.top + H * 0.72 && k.r.height < H * 0.35;
}
```

判定依据与实测数值（1440×900 视口，`BynINW_frame` 网格 `280px / minmax(400px,1fr) / 300px`）：

| 子元素 | 水平中心 cx | `cx / W` | `side` | `depth` | 实测起点 `dx` |
| --- | --- | --- | --- | --- | --- |
| `sidebarCol` | 140 | 0.097 | −1 | 0.806 | **−23.9px** |
| `centerCol` | 790 | 0.549 | 0 | 0.098 | **0px**（只做透明度 + 轻微 Y） |
| `rightbarCol` | 1290 | 0.896 | +1 | 0.792 | **+23.8px** |

**注意**：`centerCol` 的内部子元素（`[data-slot="main"]` 锚点下的会话区）如果也要入场，需要**再往下一层**用同一套几何规则处理。本方案的示例代码只处理 AppFrame 的直接子元素，这是任务要求的范围。

**不要用的判定：**

- `element.offsetLeft` / `offsetWidth` —— 受 `position` 与 offsetParent 影响，grid 项上不可靠。
- `getComputedStyle().gridColumn` —— CSS Modules 注入的规则里没有可读的列序信息。
- `[data-slot]` 的 DOM 顺序 —— `display: contents` 锚点不参与布局，顺序与视觉顺序无关。

### 3.2 由外向内的 stagger 参数建议

| 参数 | 建议值 | 依据 |
| --- | --- | --- |
| 每层延迟 `baseDelay` | **90 ms** | 三列场景下总错峰 180ms，肉眼可辨但不拖沓；实测总时长 ≈ 90 + 520 = 610ms |
| 单元素时长 `duration` | **520 ms** | 与 `cubic-bezier(0.22,1,0.36,1)` 搭配，前 40% 走完约 75% 路程，收尾柔和 |
| 横向位移 `distance` | **26 px**（再乘 `0.6 + 0.4 × depth`） | 实测侧栏 `±23.9px`、右栏 `±23.8px`；26px 上限保证不产生大面积重绘，也避免「整列飞入」的廉价感 |
| 纵向位移 | 中间列 **8 px**、底部输入框 **14 px** | 中间列几乎无横向位移，靠 Y 位移 + 透明度获得「浮现」感；底部输入框额外下沉一点，强调从下往上 |
| 缓动曲线 | **`cubic-bezier(0.22, 1, 0.36, 1)`**（easeOutQuint 近似） | 快速起步、长尾收敛，符合「由外向内」的方向感；避免 `ease-in-out` 的迟疑感 |
| 延迟公式 | `delay = baseDelay × depth + (isBottom ? baseDelay : 0)` | `depth` 越大（越靠外）越早；底部输入框最后 |
| 总时长 | **≈ 610 ms**（90 + 520） | 超过 700ms 会让人等；低于 400ms 会「糊在一起」看不出交错 |

**实测时序验证（探针 probe-frames，最终版片段）：**

| 帧 | 时间 | side | center | right |
| --- | --- | --- | --- | --- |
| 4 | 22.2ms | o=0.000, x=−23.9 | o=0.000, x=0 | o=0.000, x=23.8 |
| 5 | 39.7ms | o=0.000 | **o=0.131** | o=0.000 |
| 8 | 105.1ms | **o=0.095, x=−21.7** | o=0.575 | **o=0.106, x=21.3** |
| 23 | 355.1ms | o=0.962, x=−0.9 | o=0.989 | o=0.963, x=0.9 |
| 末帧 | 2455ms | o=1, x=0 | o=1, x=0 | o=1, x=0 |

中间列在 t≈40ms 就开始推进，而左右列到 t≈105ms 才起步——**外→内的次序被真实执行**，且末帧状态完全干净（`data-dsh-enter-ready` 已摘除、变量已清除）。

### 3.3 动画期间避免滚动条抖动 / 布局偏移（CLS）

| 措施 | 说明 |
| --- | --- |
| **只用 `transform` + `opacity`** | 二者不参与布局，不会触发 reflow。实测全程无 CLS 事件（`transform` 走合成层）。 |
| **`translate3d` 而非 `translateX`** | 显式提升为 3D 合成层，避免中途被降级。 |
| **`html[data-dsh-enter-pending] { overflow-x: clip; }`** | 元素横向位移时可能短暂超出视口产生横向滚动条。`clip` 比 `hidden` 好：不创建滚动容器、不改变 `position: fixed` 的包含块。 |
| **动画结束后立刻清理** | `finished` 回调里摘除 `data-dsh-enter-ready`、移除所有 `--dsh-enter-*` 变量、移除 `will-change`。实测末帧所有变量为空、`data-dsh-enter-ready` 已摘除。 |
| **不要动 `height`/`width`/`margin`/`padding`** | 任何影响布局的属性都会引起 reflow，进而让 grid 列重排。 |
| **`will-change` 只在动画期间存在** | 长期挂着 `will-change: transform, opacity` 会持续占用显存。本方案通过 `[data-dsh-enter-ready]` 作用域 + 播完摘除，把它的生命周期压到动画期间。 |

**一个实测中观察到的现象**：mock 页面在 `#frame` 高度设置不当（`100%` 但父级未撑满）时出现了双向滚动条，截图 `shot-40ms.png` 右侧与底部可见滚动条轨道。这恰好说明：**`overflow-x: clip` 只能防横向抖动，纵向与初始布局高度仍需宿主自身正确**——注入的脚本不该、也无法修正宿主布局。

## 4. 可直接运行的示例代码

**用法**：把下面两段分别注入。CSS 可直接作为 `<style>` 内容注入；JS 直接粘贴进 DevTools Console 或作为 `<script>` 注入。JS 会自动注入它自己的样式表（`CSS_TEXT` 常量），所以也可以**只粘 JS**。

### 4.1 CSS

```css
@layer dsh-enter-anim {
  /* 1. 只作用于被标记的 frame，避免污染其它页面 */
  #root > [data-dsh-enter-ready] > * {
    transform: translate3d(var(--dsh-enter-x, 0px), var(--dsh-enter-y, 0px), 0);
    opacity: var(--dsh-enter-o, 1);
    will-change: transform, opacity;
  }
  /* 2. 首帧即入场：浏览器在"首次样式解析"阶段就把元素放到起点，不经过中间帧 */
  @starting-style {
    #root > [data-dsh-enter-ready] > * {
      opacity: var(--dsh-enter-o0, 0);
      transform: translate3d(var(--dsh-enter-x0, 0px), var(--dsh-enter-y0, 0px), 0);
    }
  }
  /* 3. 动画期间禁掉横向滚动条抖动 */
  html[data-dsh-enter-pending] { overflow-x: clip; }
}
```

### 4.2 JS

```js
(function () {
  'use strict';
  if (window.__DSH_ENTER_ANIM__) return;
  window.__DSH_ENTER_ANIM__ = true;

  var KEY = 'dsh-enter-anim-played';
  var STYLE_ID = 'dsh-enter-anim-style';
  var CFG = {
    baseDelay: 90,   // 每层间隔 ms
    duration: 520,   // 单元素时长 ms
    distance: 26,    // 横向位移 px
    easing: 'cubic-bezier(0.22, 1, 0.36, 1)'
  };
  var CSS_TEXT = "@layer dsh-enter-anim {\n  /* 1. 只作用于被标记的 frame，避免污染其它页面 */\n  #root > [data-dsh-enter-ready] > * {\n    transform: translate3d(var(--dsh-enter-x, 0px), var(--dsh-enter-y, 0px), 0);\n    opacity: var(--dsh-enter-o, 1);\n    will-change: transform, opacity;\n  }\n  /* 2. 首帧即入场：浏览器在\"首次样式解析\"阶段就把元素放到起点，不经过中间帧 */\n  @starting-style {\n    #root > [data-dsh-enter-ready] > * {\n      opacity: var(--dsh-enter-o0, 0);\n      transform: translate3d(var(--dsh-enter-x0, 0px), var(--dsh-enter-y0, 0px), 0);\n    }\n  }\n  /* 3. 动画期间禁掉横向滚动条抖动 */\n  html[data-dsh-enter-pending] { overflow-x: clip; }\n}";
  var reduce = window.matchMedia('(prefers-reduced-motion: reduce)');

  function injectStyle() {
    if (document.getElementById(STYLE_ID)) return;
    var s = document.createElement('style');
    s.id = STYLE_ID;
    s.textContent = CSS_TEXT;
    (document.head || document.documentElement).appendChild(s);
  }

  // ---- 第一件事：抢在首帧之前挂上"待入场"状态并注入样式 ----
  if (!sessionStorage.getItem(KEY)) document.documentElement.setAttribute('data-dsh-enter-pending', '');
  injectStyle();

  // ---- 盒子判定：跳过 display:contents 的 slot 锚点与不可见元素 ----
  function box(el) {
    var cs = getComputedStyle(el);
    if (cs.display === 'contents') return null;
    if (cs.display === 'none' || cs.visibility === 'hidden') return null;
    if (parseFloat(cs.opacity) === 0) return null;
    var r = el.getBoundingClientRect();
    if (r.width < 2 || r.height < 2) return null;
    return { el: el, r: r };
  }

  function pickFrame() {
    var root = document.getElementById('root');
    if (!root) return null;
    for (var i = 0; i < root.children.length; i++) {
      var k = box(root.children[i]);          // #root 下只有 AppFrame 有盒子
      if (k) return k;
    }
    return null;
  }

  function run() {
    var f = pickFrame();
    if (!f) { document.documentElement.removeAttribute('data-dsh-enter-pending'); return; }

    var W = f.r.width, H = f.r.height, frame = f.el;
    frame.setAttribute('data-dsh-enter-ready', '');

    // ---- 由外向内的 stagger：按水平中心到画面中心的距离排序 ----
    var items = [];
    for (var i = 0; i < frame.children.length; i++) {
      var k = box(frame.children[i]);
      if (!k) continue;
      var cx = k.r.left + k.r.width / 2;
      var side = cx < W * 0.45 ? -1 : (cx > W * 0.55 ? 1 : 0);   // 左列从左侧入、右列从右侧入
      var depth = Math.min(1, Math.abs(cx / W - 0.5) * 2);        // 0 = 画面中心，1 = 最外
      var isBottom = k.r.bottom > f.r.top + H * 0.72 && k.r.height < H * 0.35;
      items.push({
        el: k.el,
        dx: side * CFG.distance * (0.6 + 0.4 * depth),
        dy: isBottom ? 14 : (depth > 0.85 ? 0 : 8),
        delay: CFG.baseDelay * depth + (isBottom ? CFG.baseDelay : 0)
      });
    }
    if (!items.length) { document.documentElement.removeAttribute('data-dsh-enter-pending'); return; }

    // ---- 先把起点写进 CSS 变量，让 @starting-style 有值可用 ----
    items.forEach(function (it) {
      it.el.style.setProperty('--dsh-enter-x0', it.dx + 'px');
      it.el.style.setProperty('--dsh-enter-y0', it.dy + 'px');
      it.el.style.setProperty('--dsh-enter-o0', '0');
      it.el.style.setProperty('--dsh-enter-x', '0px');
      it.el.style.setProperty('--dsh-enter-y', '0px');
      it.el.style.setProperty('--dsh-enter-o', '1');
    });

    function cleanup() {
      sessionStorage.setItem(KEY, '1');
      document.documentElement.removeAttribute('data-dsh-enter-pending');
      frame.removeAttribute('data-dsh-enter-ready');
      items.forEach(function (it) {
        ['--dsh-enter-x0', '--dsh-enter-y0', '--dsh-enter-o0',
         '--dsh-enter-x', '--dsh-enter-y', '--dsh-enter-o'].forEach(function (p) {
          it.el.style.removeProperty(p);
        });
      });
    }

    // ---- 双 rAF：让起始状态先落一次样式，再交给 WAAPI 接管 ----
    requestAnimationFrame(function () {
      requestAnimationFrame(function () {
        document.documentElement.removeAttribute('data-dsh-enter-pending');
        var running = items.map(function (it) {
          return it.el.animate(
            [
              { opacity: 0, transform: 'translate3d(' + it.dx + 'px,' + it.dy + 'px,0)' },
              { opacity: 1, transform: 'translate3d(0px,0px,0)' }
            ],
            { duration: CFG.duration, delay: it.delay, easing: CFG.easing, fill: 'backwards' }
          );
        });
        var last = running[running.length - 1];
        if (last) last.finished.then(cleanup, cleanup); else cleanup();
      });
    });
  }

  function boot() {
    if (sessionStorage.getItem(KEY)) { document.documentElement.removeAttribute('data-dsh-enter-pending'); return; }
    if (reduce.matches) {
      sessionStorage.setItem(KEY, '1');
      document.documentElement.removeAttribute('data-dsh-enter-pending');
      return;
    }
    var tries = 0;
    (function wait() {                     // 等 React 把 frame 挂上来
      if (pickFrame()) return run();
      if (++tries > 200) { document.documentElement.removeAttribute('data-dsh-enter-pending'); return; }
      requestAnimationFrame(wait);
    })();
  }

  if (document.readyState === 'loading') document.addEventListener('DOMContentLoaded', boot, { once: true });
  else boot();
})();
```

### 4.3 实测验证结果

在模拟 DSH `AppFrame` 网格结构（`280px / minmax(400px,1fr) / 300px`，1440×900）的页面上，用无头 Chrome 154 + CDP 逐帧采样 + 截图验证：

| 验证项 | 结果 |
| --- | --- |
| 首帧是否闪 | **无**。第 1–3 帧为设置阶段，第 4 帧（t=22.2ms）三列同时处于起点；没有任何一帧出现「终值态」 |
| 方向是否正确 | 侧栏 `x=−23.9px` 向左、右栏 `x=+23.8px` 向右、中间 `x=0` |
| 交错是否成立 | center 在 t≈40ms 起步，side/right 在 t≈105ms 起步 |
| 结束时是否干净 | 末帧 `opacity:1`、`x=0`、`data-dsh-enter-ready` 已摘除、`--dsh-enter-*` 全为空 |
| 只播一次 | 首载 `readyFrames=38 / movedFrames=30`；reload 后 `0 / 0` |
| 减少动效 | `--force-prefers-reduced-motion` 下 `movedFrames=0`，无标记残留 |
| 视觉证据 | `shot-40ms.png`（左右列融入背景、中间半透明）、`shot-240ms.png`（左右列半透明浮现）、`shot-900ms.png`（全部到位） |

**未验证的部分（如实标注）：**

- 在**真实 DSH 窗口**中的观感与性能未验证。原因：DSH Web GUI（`http://127.0.0.1:19387`）需要鉴权（实测返回 `401 dsh web authentication required`），本机 headless Chrome 无法直接接入；直接打开解包产物 `dist/index.html` 也因缺少宿主注入的 `window.__ModuleLoader__` 启动门面而无法引导（实测控制台报 `web boot: window.__ModuleLoader__ bootstrap facade is missing`）。因此验证是在**结构等价**的 mock 页面上完成的。
- 「注入时机晚于 React 首次挂载」时的表现未实测，理论上会闪一次（见 2.2 末段）。
- 真实 DSH 的 AppFrame 子元素数量随运行态变化（`data-shell-leading`、`DragHandle` 条件渲染），几何判定的边界情形（例如侧栏折叠到极窄）未逐一实测。
