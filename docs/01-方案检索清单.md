## 0. 一手实测基准：本机 Steam 客户端的官方启动动画

本次检索最硬的一条证据不在网上，而在本机 —— Steam 客户端内置了官方启动动画文件，可直接读取其容器元数据。

**样本路径**：`C:\Program Files (x86)\Steam\steamui\movies\`

| 文件 | 字节数 | 编码 | Track 分辨率 | 时长 |
| --- | --- | --- | --- | --- |
| `deck_startup.webm` | 1840847 | V_VP9 | 450×450 | 4.008s |
| `oled_startup.webm` | 764649 | V_VP9 | 450×450 | 4.000s |
| `startup_machine.webm` | 320937 | V_VP9 | 1920×1080 | 3.117s |
| `bigpicture_startup.webm` | 1338011 | V_VP9 | 1920×1200 | 6.000s |
| `deck-suspend-animation.webm` | 160008 | V_VP9 | 450×450 | 1.000s |

**测量方法**（可复现）：直接扫描 WebM/Matroska 的 EBML 元素 —— `Duration`(id 0x4489，Segment/Info 内，TimecodeScale=1ms)、`PixelWidth`(0xB0) / `PixelHeight`(0xBA)（Video 元素内）、`CodecID`(0x86)。

**交叉验证**：① `bigpicture_startup.webm` 的扫描结果 1920×1200 与 Windows Shell 媒体属性读取值完全一致，证明扫描法有效；② `deck_startup.webm` 的 Duration 原始值 4008 与 Shell 读取的 4.008s 一致。

**由此得到的三条工程事实**：

1. **官方开机动画的时长基准 ≈ 4.0 秒**，且 LCD（deck_startup）与 OLED（oled_startup）两代完全一致 —— 4.008s 与 4.000s。这不是「越长越炫」的路线，而是一个约 4 秒的确定时长。
2. **官方开机动画的 Track 是 450×450 的方形容器**（两代一致），并非屏幕原生的 1280×800 —— 说明播放层存在缩放行为。社区替换经验要求「1280×800、16:10」（见 A3），两者差异说明：**自绘启动动画应按窗口/屏幕宽高比制作，而不是照抄官方容器的方形比例。**
3. **1840847 字节 = 社区流传的 truncate 目标值**（见 A2），与官方 `deck_startup.webm` 的实际字节数完全吻合 —— 印证了社区替换手法确实是在「等长覆盖官方文件」这一机制上运作的。

**主 Agent 复核补充（2026-10-03，独立复扫同一目录）**：主 Agent 用自写的 EBML 扫描器把该目录**全部 22 个 webm** 重扫了一遍，复现了上表全部数值，并发现子代理漏扫的 3 个**与「开机动画」语义更直接相关**的官方文件：

| 文件 | 字节数 | 分辨率 | 时长 |
| --- | --- | --- | --- |
| `steam_os_family_startup.webm` | 733124 | 1024×1024 | **8.948s** |
| `steam_os_startup.webm` | 332642 | 1920×1200 | **5.000s** |
| `steam_os_suspend.webm` | 74707 | 450×450 | 2.000s |

**这三条修正了原结论的适用范围**：`4.008s / 4.000s` 是 **Steam Deck 掌机**的开机动画时长，**不是 SteamOS 的通用规格** —— Steam 客户端在大屏场景下的开机动画是 **5.000s（`steam_os_startup`）**，家族级启动片头甚至到 **8.948s**。同时也可见官方在**同类动画上按场景给出多个时长档**（1.0s 挂起 / 3.0–4.5s 控制器演示 / 4.0s 掌机开机 / 5.0s 桌面开机 / 8.9s 家族片头）。

**对 DSH 的意义**：Valve 并非「所有启动动画都 4 秒」，而是**按场景分档**。DSH 桌面版属桌面大屏场景，参照档位应是 **`steam_os_startup` 的 5.0s 量级**，而不是掌机的 4.0s。本实现取 **约 5.6s（不含等待 UI 就绪的时间）**，落在该量级内。

### A6. ValveSoftware/steam-for-linux 的两个 issue：动画 → UI 的过渡如何发生

- **URL**：
  - https://github.com/ValveSoftware/steam-for-linux/issues/11655 （实读 API 正文）
  - https://github.com/ValveSoftware/steam-for-linux/issues/11715 （实读 API 正文）
- **关键原文摘录**：
  - #11655（SteamOS 3.6）：`I can see black screen for the first 2/3 seconds and sound of boot video in the background. After that, I see on the screen the end of animation. Only the default boot video works properly`
  - #11715（SteamOS 3.6.20，LCD）：`Custom startup movie doesn't play when restarting. Valve built-in startup movie does play on restarts, but not custom. … You can hear the movie's audio playing only the external monitor screen is black.`
- **这两条说明了什么（区分事实与推断）**：
  - **事实**：启动视频的音轨会先于画面输出（「只听到声音、屏幕黑」）；视频播放层与 UI 输出层是**相互独立、并行初始化**的；默认动画在同样条件下能正常显示，自定义动画更容易踩到这个窗口。
  - **推断（标注为推断）**：SteamOS 3 的「动画结束 → 桌面出现」**不是交叉淡出**，也没有可感知的统一过渡层 —— 视频播完（或被打断）后直接露出 Gamepad UI，表现为硬切；用户感知到的「黑屏 2–3 秒」正是视频层已就绪、而合成/输出层尚未就绪的窗口。
  - **另一条推断**：动画时长与 UI 就绪时间存在竞争关系 —— 若 UI 早于动画播完就绪，动画会被截断；若 UI 晚于动画，则出现黑屏等待。这解释了为什么官方把默认动画压到约 4 秒（§0 实测）。
- **可复用于本任务的点**：
  - DSH 的启动动画**必须与主 UI 渲染解耦**：先出一个不透明底色的窗口 + 动画层，再让 React 首屏在背后完成挂载。这正是 C2 里 Electron 官方「backgroundColor + 立即 show」的建议所对应的做法。
  - 动画结束与 UI 出现之间**显式设计一个过渡**（例如 150–250ms 的淡出），而不依赖「谁先就绪谁先上」的运气 —— 这是 DSH 相比 SteamOS 可以做得更好的地方。

### A9. 特别查明的三项结论（汇总）

**① Steam Deck 官方开机动画的实际画面内容与时长**
- 时长（实测）：`deck_startup.webm` = **4.008s**；`oled_startup.webm` = **4.000s**；`startup_machine.webm` = 3.117s；`bigpicture_startup.webm` = 6.000s（大屏模式启动时播放，见 A7 的「桌面模式下大屏幕模式启动时播放」）。
- 容器事实：VP9、450×450（两个开机动画）。文件名固定为 `deck_startup.webm`，位于 `Steam\steamui\movies\`。
- **画面内容：未取得可引用的一手来源。** 本机不具备抽帧能力（§0），Steam 官方页 / YouTube / Reddit 在本机网络下抓取失败（§D）。**故本文不对官方画面构图（黑底/居中 logo/几何线条等）作任何断言** —— 需要时请直接查看本机文件。

**② SteamOS 3 里「动画结束 → 桌面出现」的过渡方式**
- 事实层面：音画分离、动画层与 UI 层并行初始化（A6 两个 issue 的原文）。
- 推断层面：**硬切，而非淡出**；黑屏等待来自「动画播完但 UI 尚未合成输出」的窗口期。
- 对 DSH 的行动项：显式加一个短淡出（150–250ms），并把底色与动画首帧统一，避免出现「黑屏 — 突然出 UI」的断裂。

**③ 自定义开机动画的格式与时长限制（反推官方工程约束）**
- 格式：`.webm`（A2、A3），编码 VP8/VP9（Steam 社区讨论摘要中出现「must be in `.webm` format with VP8 or VP9 codec」，该条为搜索摘要，未取得页面原文，仅作旁证）。
- 比例：**1280×800、16:10**（A3 实读原文），与 Steam Deck 屏幕一致。
- 文件位置：官方 `steamui/movies/`（A2、A3）；用户覆盖 `~/.steam/root/config/uioverrides/movies`（A4、A5）。
- 文件长度约束：**必须与原文件等长**（`truncate -s 1840847`，A2/A3 实读；且 1840847 与 §0 实测字节数完全一致）。这是「等长占位」的工程约束，不是视频本身的限制。
- **最大秒数：未找到任何官方或可引用的硬性上限。** 检索到的所有证据都指向「没有硬上限，但会被 UI 就绪时刻打断」（A6）。请勿采信「最长为 X 秒」的说法 —— 本次检索未找到支撑。
- 反推结论：官方真正在意的约束是 **① 比例匹配 ② 文件可等长覆盖 ③ 播放独立于 UI**，而不是时长上限。

### C1. SVG 线条描画：让「线长成图形」

**来源 1**：Jake Archibald《Animated line drawing in SVG》
- **URL**：https://jakearchibald.com/2013/animated-line-drawing-svg/ （实读，剥离后 5390 字符）
- **关键原文摘录**：
  - `stroke-dasharray lets you specify the length of the rendered part of the line, then the length of the gap. stroke-dashoffset lets you change where the dasharray starts.`
  - `Drag both sliders up to their maximum, then slowly decrease the dashoffset. Voilà, you just made the line draw!`
  - 取长度：`var path = document.querySelector('.squiggle-container path'); path.getTotalLength(); // 988.0062255859375`
  - `Avoid using SMIL, it also isn't supported in IE and doesn't perform well in Chrome & Safari`
  - 用 CSS transition/transition 实现；先 `transition = 'none'` 清旧过渡，再设 `strokeDasharray = length + ' ' + length`、`strokeDashoffset = length`，然后触发一次布局再开始动画
- **可复用于本任务**：启动动画的核心手法。**要点是「先用同一长度同时设置 dasharray 与 dashoffset（制造不可见状态），再触发一次重排，最后把 dashoffset 归零」** —— 少了中间那次强制布局，动画会静默失效（这是最常见的坑）。

**来源 2**：CSS-Tricks《How SVG Line Animation Works》
- **URL**：https://css-tricks.com/svg-line-animation-works/ （实读，剥离后 9322 字符）
- **关键原文摘录**：
  - `.path { stroke-dasharray: 1000; stroke-dashoffset: 1000; animation: dash 5s linear forwards; } @keyframes dash { to { stroke-dashoffset: 0; } }`
  - `If doing it with CSS, you'll want the animation to have animation-fill-mode of forwards so the final state remains how the animation ends.`
  - `You just need to make stroke-dasharray a longer value than the length of the stroke.`
  - `Most of the examples you see of SVG line animations use JavaScript. That's because it's hard to know what the length of that stroke actually is.`
  - 评论区 Antonio 的实测反馈：`I could not get the total length from non-paths. So I made a little thing to convert all the non-paths into paths first`
- **踩坑清单（两条来源合并）**：
  1. **`getTotalLength()` 只对 `<path>` 有效**，`<circle>`/`<rect>`/`<line>` 取不到 → 先用路径工具把图形转成 path（对 DSH：SVG 一律用 `<path d="...">` 绘制 logo 与线条）。
  2. **必须带 `forwards`（或 `animation-fill-mode: forwards`）**，否则动画结束会弹回不可见状态。
  3. **`stroke-dasharray` 要 ≥ 实际路径长度**，否则线条会分成两段。
  4. 长度值可以硬编码（省掉 JS），但换 viewBox 缩放后要重新核对 —— 用相对单位或运行时计算更稳。
  5. **不要用 SMIL**（`<animate>`）：性能与兼容性都更差，用 CSS transition / animation。

### C2. Electron 启动白屏：成因与规避

**来源 1**：Christian Engvall《Electron white screen app startup》
- **URL**：https://www.christianengvall.se/electron-white-screen-app-startup/ （实读，剥离后 2884 字符）

**来源 2**：Electron 官方 BrowserWindow 文档
- **URL**：https://www.electronjs.org/docs/latest/api/browser-window （实读，剥离后 24879 字符）

### C3. 批量元素 stagger 入场且不触发 layout thrash

**来源 1**：CSS-Tricks《Staggered CSS Transitions》
- **URL**：https://css-tricks.com/staggered-css-transitions/ （实读，剥离后 10171 字符）
- **关键原文摘录**：
  - 逐项延迟：`.list li:nth-child(1) span { transition-delay: 0.0s; } … :nth-child(6) { transition-delay: 0.25s; }`（0.05s 步长）
  - 用变量驱动：`.list { --delay: 0.05s; }` + `transition-delay: calc(var(--delay) * 3)`
  - 局限：`Say your list starts to grow, perhaps to seven or more items. The staggering suddenly isn't working on the new ones because this doesn't account for that many list items.`
- **可复用于本任务**：**这是零依赖错峰入场的标准手法** —— 但避开 `nth-child` 的硬编码上限，改为在渲染时给每个面板写 `style="--i: 3"`，CSS 里统一 `transition-delay: calc(var(--i) * 60ms)`（数值取自 B7 的 13.5）。

**来源 2**：MDN《Animation performance and frame rate》
- **URL**：https://developer.mozilla.org/en-US/docs/Web/Performance/Animation_performance_and_frame_rate （实读）
- **关键原文摘录**：
  - `For a rate of 60 frames per second, the browser has 16.7 milliseconds to execute scripts, recalculate styles and layout if needed, and repaint the area being updated.`
  - 渲染瀑布：`Recalculate Style → Layout → Paint → Composition`
  - 高代价属性（触发 style + layout + repaint）：`left, max-width, border-width, margin-left, font-size`
  - 走合成、连 repaint 都不触发的属性：`transform, opacity`
- **可复用于本任务**：**面板入场只动 `transform` 与 `opacity`** —— 这既是性能要求，也正好是「由外向内平移」的实现方式（`transform: translate3d()` 而非 `left/top`）。

**来源 3**：emilkowalski/skills · performance-cheatsheet.md + animate/SKILL.md（同一套来源，见 B6）
- **关键原文摘录**：`Motion's x/y drops frames → Animate the full transform string instead`；`CSS animations beat JS under load — they run off the main thread, while requestAnimationFrame-based animation drops frames while the browser loads, scripts, or paints.`；`Use CSS for predetermined motion, JS for dynamic and interruptible motion.`
- **可复用于本任务**：
  - **启动动画是「预定序列」→ 用纯 CSS animation/keyframes**；面板入场是「可被打断的交互」→ 优先 CSS transition（transition 会从当前值重定向，keyframes 会从零重启）。
  - **批量入场不要用 JS 逐帧驱动**，也不要只用 `x/y` 简写这类非合成路径；写成完整 `transform: translate3d(...)` 字符串。
  - 不要和昂贵工作在同一个 tick 里启动动画：先启动动画，让一帧落地，再做重活（对 DSH：启动动画层先动，首屏数据加载延后一拍）。

## E. 最值得直接复用的 3 条

**① emilkowalski/skills 的曲线与时长令牌（B6）**
理由：它是本次检索中**数值密度最高、且与零依赖约束完美兼容**的一条 —— 三组曲线直接以 CSS 变量形式给出（`--ease-out: cubic-bezier(0.23,1,0.32,1)`、`--ease-in-out: cubic-bezier(0.77,0,0.175,1)`、`--ease-drawer: cubic-bezier(0.32,0.72,0,1)`），外加「UI 动画 <300ms」「禁止 ease-in」「30–80ms stagger」「禁止凭手感编曲线」四条硬规则。可以直接落成 DSH 的 `animation-tokens.css`，两套动画共用。

**② joepUI/motion-ref-skill 的 13.5 + 13.7 组合（B7）**
理由：任务里的「由外向内平移入场」几乎就是它的原样配方 —— **横向滑入 250–400ms / ease-out / 局部元素位移 20–40px**（13.7）+ **`animation-delay: calc(var(--i) * 60ms)`、单项 300ms、总时长 <800ms、超过 6 个元素就缩小间隔**（13.5），且明确给出 `prefers-reduced-motion` 的降级（13.1 淡入 200–400ms）。中文表述、CSS 变量写法，迁移成本最低。

**③ 本机实测的官方启动动画基准 + Electron 官方白屏结论（§0 + C2）**
理由：这一条同时解决了「做多长」和「怎么不白屏」两个决策 —— 官方开机动画实测为 **4.008s / 4.000s（两代一致）**，说明 4 秒是经过验证的产品节奏（对应 B1 的 Dramatic reveal 区间）；而 Electron 官方文档明确说「复杂应用不要等 `ready-to-show`，立即 show 并设置接近应用背景的 `backgroundColor`」。两者结合，DSH 的启动动画应当**立即显示一个深色窗口、在页面内自绘动画、与 React 首屏并行、结束前显式淡出交接**（A6 的 SteamOS 教训正是反面教材：音画先行、UI 后到，导致黑屏）。
